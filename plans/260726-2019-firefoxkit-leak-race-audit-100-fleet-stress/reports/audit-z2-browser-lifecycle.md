# Audit Z2 — Browser Lifecycle (leak/race, static, read-only)

Scope: `browser.go`, `browser_context_lifecycle.go`, `browser_spawn.go`, `browser_waitpage.go`,
`browser_connect.go`, `browser_launch.go`, `browser_pages.go` (+ `page.go` cleanup, `internal/bidi`
for context). No `.go` file modified.

## Findings

| Z2-1 | `browser_context_lifecycle.go:64-73` | unbounded-growth | P2 | Fallback runs `target.cleanup(cctx)` **on the subscription worker**. `cleanup` issues 3 sequential Sends (`page.go:117`, `:136`, `:158`); `writeJSON` ignores the 3s `cctx` and uses its own 10s budget (`transport.go:61-72`, `:93`) → up to ~30s wedge per event on a hung peer. During that wedge `dispatch` drops `contextDestroyed` at the 256-cap queue (`events.go:20`, `:160-167`) → dropped pages never leave `b.pages`. This is exactly the failure the drainer was built to prevent (comment `:51-54` claims it "can never" happen). Untested: the flood test uses 300 events vs `cleanupChCap`=512 (`browser_context_lifecycle_load_test.go:33`), so the fallback branch never executes in CI. | On saturation, drop the cleanup (page is already detached) or hand it to a single overflow goroutine — never run RPCs on the subscription worker. | high |
| Z2-2 | `browser_waitpage.go:39-51` + `:63-73` | memory-leak | P2 | `GetTree` snapshot → `bindNewContext` is not atomic w.r.t. `contextDestroyed`. | Z2-3 | `browser_context_lifecycle.go:117-128` vs `:139-149` | race | P2 | `Browser.Close` calls `baseCancel()` (`browser.go:140-142`) **before** `signalCleanupDrainer()` (`:149`). So the graceful drain is honored only ~half the time, nondeterministically. | Z2-6 | `browser_context_lifecycle.go:64-66` | memory-leak | P3 | After `signalCleanupDrainer` the workers exit, but the subscription is still live until `client.Close()` (`browser.go:176`); `removeDestroyedPage` keeps succeeding on the buffered `cleanupCh` with no receiver. ## Clean areas (checked, no finding)

- **Double-Close**: `Browser.Close` under `closeOnce` (`browser.go:137`); `bidi.Client.Close` idempotent via `shutdownOnce`/`finishOnce` (`client.go:190-207`); `Page.cleanup` guarded by `cleanedUp.Swap` (`page.go:105`); `signalCleanupDrainer` nil-safe when the watch never started (`browser_context_lifecycle.go:157-159`).
- **`b.pages` locking**: all 20 access sites grep-verified under `pagesMu` (incl. every `range`) — `browser.go:81/88/150`, `browser_pages.go:21/40/51/80/93/124/146/157`, `browser_context_lifecycle.go:80`, `browser_waitpage.go:64/79`, `page.go:293`. `Page.URL()` is a cheap `p.mu.RLock` (`page.go:202-209`), so holding `pagesMu` across it is safe; no reverse `p.mu → pagesMu` order exists.
- **Drainer start/stop ordering**: `SubscribeEvents → startCleanupDrainer → Subscribe` (`browser_context_lifecycle.go:32-46`) means the handler can never observe a nil `cleanupCh`; `cleanupWG` balanced (`Add` at `:114`, `defer Done` at `:116`).
- **`closeAll` vs `remove` double-close**: `closeAll` clears `handlers` under `Lock` before closing channels (`events.go:127-139`), so a concurrent `Unsubscribe` from inside `Page.cleanup` finds nil — no close-of-closed panic, no lock inversion (mu released before `wg.Wait`).
- **`Browser.Close` boundedness**: graceful phase capped at 2s (`browser.go:160-173`) and the sweep ctx at 3s (`:163`); post-`client.Close` `cleanupWG.Wait()`/`<-graceful` unblock because `drainPending` runs before `closeAll` (`client.go:202-207`), so wedged Sends get `ErrClientClosed`.
- **Launch failure paths**: profile dir removed on every exit — `writeUserPrefs` (`:56`), `StderrPipe` (`:64`), `Start` (`:76`), and via `cleanup()` for discover/dial/`NewSession` (`:81-85`, `:92/102/117`); `populateInitialPage` failure routes through `b.Close()` (`:139`). No zombie: `cleanup()` does `Kill`+`Wait`. Probe goroutine exits on `ctx.Done` (`:340-341`).
- **`Spawn`**: single `cmd.Wait()` goroutine closing `s.done` (`browser_spawn.go:56-59`); `PID`/`Kill` nil-guarded (`:86-103`); `Kill` idempotent; no temp profile to leak (`userDataDir` is caller-supplied and required, `:31-33`); stdout/stderr unset → no pipe-fill.
- **`WaitForNewPage` handler hygiene**: registers **no** BiDi handler and spawns **no** goroutine (poll-only), so there is no deregistration or channel-leak path on the timeout branch — the concern in the brief does not apply to this implementation.
- **`Connect`**: `client.Close()` on `NewSession` failure (`browser_connect.go:52`); `closeProc:false` so `Close` never kills a foreign process.

## Unresolved questions

1. Z2-3: was `b.ctx()` in the worker's normal branch intentional (`browser_context_lifecycle_load_test.go:113` comment relies on base-ctx cancel to unblock the join) or an oversight vs `drainRemainingCleanup`'s `Background`? Fixing it may slow that join.
2. Z2-1: acceptable to drop cleanup entirely on saturation, or must every detached page get a best-effort RPC?

**Status:** DONE
Ten findings with file:line evidence — two P2 correctness bugs in never-audited `WaitForNewPage`
(binds already-destroyed contexts; `timeout` overshoots to the 60s command backstop) plus a P2
head-of-line-blocking hole in the cleanup drainer's inline fallback that CI does not cover. Double-Close
safety, `pagesMu` discipline across all 20 access sites, and Launch/Spawn failure-path teardown are clean.
